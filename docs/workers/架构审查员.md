## 三、职责定义

| 审查维度 | 检查项 |

| 可扩展性 | 对需求变更的适应能力、开闭原则 |

## 五、Prompt 模板库

### 5.1 架构评审

```
请从前端架构角度评审以下代码：

评审维度：
1. 组件设计：SRP 原则、组件粒度、Props 设计
2. 状态管理：Store 结构、数据流向、副作用管理
3. Composable 设计：复用性、入参设计、返回值
4. 依赖关系：模块间方向、循环依赖检测
5. 可测试性：纯函数比例、依赖注入
6. 可扩展性：需求变更适应能力

文件：{文件路径}

输出：
- 架构图（文本描述）
- 问题列表（按严重程度排序）
- 重构建议（含代码示例）
```

### 5.2 组件拆分建议

```
分析 {组件名} 组件，评估是否需要拆分：

判断标准：
1. 代码行数 > 300 行？
2. Props > 10 个？
3. 处理 > 2 个不相关的功能？
4. 嵌套 v-if/v-for > 3 层？

如需拆分，请给出：
- 子组件划分方案
- 父子通信设计
- 状态提升策略
```

### 5.3 状态管理评审

```
评审 {Store名} Pinia Store 的设计：

检查：
1. State 结构是否扁平化
2. Getters 是否过度计算
3. Actions 是否承担了过多职责
4. 异步逻辑的错误处理
5. Store 间依赖是否合理
6. $reset() 是否覆盖所有状态
```

## 六、微调建议

| 项目规模 | 重点关注 |
|---------|---------|
| 小项目 | 避免过度设计，简单直接 |
| 中项目 | 模块化、composable 复用 |
| 大项目 | 分层架构、依赖注入、微前端 |
| 组件库 | API 设计、扩展性、向后兼容 |
